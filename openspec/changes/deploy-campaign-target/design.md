## Context

The current engine contracts are in `openspec/specs/fleet-deploy/spec.md`. In `crates/mandala-core/src/engines/deploy.rs`, `plan_run_with_boot` resolves the inventory limit, separates non-deploy members and validates flattened settings before `register_run` writes `meta.json`. `build_profiles_with` resolves derivations, builds those exact derivations once, and `recover_profiles` probes the exact outputs without building or substitution. `fan_out_with` consumes verified successes. This protects one attempt, not an operator's multi-attempt campaign.

`crates/mandala-core/src/registry.rs` provides atomic metadata writes, per-run observation, liveness and count/age retention. Successful host events are sticky within one run; there is no campaign-level outcome history. `Inventory::resolve` and `to_limit` in `crates/mandala-core/src/inventory.rs` flatten selector algebra to sorted names, losing exclusion rationale. `reboot_argv` in `crates/mandala-core/src/runner.rs` dispatches the fleet's `ans-reboot` app with a concrete limit and existing order/drain options, independently of deploy targets.

`crates/mandala-core/src/drift.rs` caches evaluated toplevels in `.expected.json`. `cache_fresh` accepts the same clean revision, never a dirty revision. `compare` already distinguishes installed-but-not-current expectations and boot-critical differences; without an expectation its final branch can still report in-sync. CLI `run_drift` in `crates/mandala-core/src/cli.rs`, TUI refresh/selection logic in `crates/mandala-tui/src/app.rs`, and MCP `tool_drift` in `crates/mandala-mcp/src/server.rs` must share the stronger unknown-expectation judgment.

Existing run inspection uses TUI runs/attachment, CLI `tui deploy --attach`, and MCP `deploy_status`. These are not yet campaign retry interfaces. Preserve their shapes and meanings. Additive metadata and event conventions, including the empty-host controller stream, follow `openspec/specs/fleet-state-formats/spec.md` and `openspec/changes/deploy-cache-publish/design.md`.

## Goals and Non-goals

Make one campaign's target durable, identifiable and stable across attempts, explicit skips, reboots, verification, source movement and frontend restarts. Keep old runs readable and preserve successful work. Non-goals are implementation, consumer changes, HA rollout planning and cache publishing changes. Plan approval and implementation authorization remain separate from completing these artifacts.

## Decisions

### 1. Capture one immutable source, not a revision label

A version-1 campaign target contains:

| Field | Meaning |
| --- | --- |
| `campaign_id`, `schema_version`, `created_at` | Generated confined identifier, independent schema version, UTC creation timestamp |
| `source` | Canonical local checkout identity or sanitized immutable remote reference, root revision when available, dirty boolean, materialized source store path and content/NAR digest, lock digest, and recursively resolved input identities |
| `source.inputs` | Entries keyed by full input path, with resolved content digest/store identity and revision when available; follows edges are resolved, not merely named |
| `source.submodules` | Relative path, recorded gitlink revision, actual checked-out revision, recursive dirty state and captured content identity for each source-relevant submodule |
| `selection` | Original selector for explanation, sorted exact pre-exclusion members and deploy-capable subset; selector exclusions resolved to names with reasons |
| `hosts` | For every deploy-capable selected member: exact intended deploy-profile output path, exact system-toplevel expectation, derivation/output identity for realization, and captured flattened execution settings and effective activation mode |
| `initial_exclusions` | Exact names, nonempty reasons, actor and timestamp; includes authored skips and explicit non-deploy-capable notices with distinct reason codes |
| `target_digest` | Content digest covering the immutable target, including initial exclusions, independent of later outcomes |

The deploy profile may wrap the system toplevel: persist both and never compare `/run/current-system` to a wrapper path. Resolve the pair from the same frozen evaluation and validate their correspondence before allowing host effects. A build failure does not erase its known intended output path. A missing/static-unknown output prevents binding, not an opportunity to fill it from a later source.

Materialize a Nix-compatible source snapshot first, including effective dirty content and relevant nested local inputs/submodules. Evaluate inventory, settings and profile identities only from that frozen input graph, using a fresh or content-keyed evaluator; root the snapshot, required derivations and realized outputs for the open campaign's lifetime. Record dirty state for explanation but use content identities for equality: two different dirty trees at one revision are different sources. Include source-relevant untracked files when Nix would include them; do not hash ignored files into a fictitious Nix input. Impure/environment-dependent evaluation is refused for campaigns unless all influencing inputs can be captured in the identity; ordinary legacy deploy remains unchanged.

Capture source identities around materialization and binding. If the checkout or any effective input moves during capture, reject with a source-changed diagnostic and do not publish a ready campaign or launch a run. Do not auto-retry capture against a new source. Once a target is atomically bound, ongoing attempts consume the snapshot and recorded derivation/output paths only; a later checkout edit cannot affect them. Every new continuation performs another source comparison; a mismatch or unavailable identity is explicit and blocks new host effects pending a new campaign. An in-flight attempt may finish against its already bound source and reports observed source movement separately.

**Alternatives:** revision plus `-dirty` is insufficient because dirty content and nested pointer movement can differ at the same root revision. Hashing only the root lock file misses mutable local inputs and submodules. Rechecking a mutable checkout between individual builds still leaves races; use frozen content as the evaluation authority. Keeping only output paths loses provenance and cannot safely realize missing outputs.

### 2. A campaign is not a mutable run

Store campaigns under `state_dir()/campaigns/<campaign-id>/campaign.json`, separate from `runs/<run-id>/`. Use 1-space sorted JSON with no trailing newline and write-then-rename, consistent with existing metadata. `schema_version: 1` belongs to this new document, not the JSONL event version. One atomic manifest contains the immutable target, lifecycle, monotonic generation, ordered exclusion updates, linked attempts, retained outcome evidence and verification results. The immutable target never changes after binding. Unknown fields are ignored; unsupported schema versions permit identification but refuse mutation and any target-dependent judgment. Corruption/missing manifests mean unavailable, never a fresh target.

Each deploy/reboot/verification attempt remains an ordinary registry run with additive `campaign_id`, `campaign_target_digest`, `campaign_generation`, `campaign_attempt` and resolved eligible `targets`. Capture the exclusion generation at dispatch. Do not reuse a run id, truncate old JSONLs, reset terminal host events, or reinterpret existing `rc`, `boot`, `publish`, `targets` or `skipped`. Campaign summaries retain per-host outcomes with producing run/attempt identity even if detail is later pruned. Attempt states include prepared, running, settled and orphaned/unknown; these do not add host terminal events. Any campaign controller stream uses a supported EventWriter version and an empty host tag with `actor: controller`, never an invented fleet member.

Publish a prepared attempt reference durably before launch and record the run link before host effects. Recover interrupted allocation by inspecting the linked registry/supervisor, not relaunching it. Uncertain ownership/outcome blocks scheduling until explicit read-only reconciliation determines failed/pending versus still active. Retain existing process liveness and terminal-failure precedence; a closed campaign is not a live process and a dead frontend does not settle a live attempt.

**Decided retention policy:** protect open campaigns and their linked runs/GC roots from ordinary count/age pruning, even between attempts. Protect live/supervised allocations exactly as today. After explicit close, treat the campaign plus its linked inactive runs as a retention unit using existing keep/age policy, aged from `closed_at`; a live linked run still prevents pruning. Legacy runs continue under existing retention unchanged. Close does not immediately delete records or unroot a live attempt. No campaign launch may run through an unmodified retention writer that could prune protected runs; upgrade all participating writers before enabling campaign creation.

**Alternatives:** embedding everything in the first run's `meta.json` makes normal run retention and reboot links unsafe. Rewriting the first run during retries destroys historical failure evidence. Keeping every campaign forever avoids deletion races but silently defeats the operator's retention policy; explicit close releases protection instead. A lease/expiry would bound disk use but needs separate renewal and expired-target UX; version 1 protects open campaigns until close and surfaces retained roots/open campaigns rather than silently expiring them.

### 3. Retry eligible work, never successful activations

A campaign is open or closed. **Decided start semantics:** creation binds the target and starts the first deployment attempt in one operation, after the normal real-mutation confirmation gate and dispatch revalidation. Binding and the prepared attempt/run link are durable before host effects. An explicit dry creation preview binds and displays the target without launching an attempt or performing host effects; real work remains pending and can later be dispatched with retry. This preview is not the normal real create-and-deploy path. `retry` creates a new attempt from the immutable selected deploy members minus effective exclusions, intersected with failed (including rolled-back) or pending members. A supplied selector can narrow that set, never widen it or re-resolve group membership from the latest inventory. New members require a new campaign. Successful `confirmed` and `reboot-pending` outcomes persist and are not built/copied/activated again. Dry activation results are previews, not successful real deployments; they leave real work pending.

Reuse exact intended paths and captured settings. Realize missing outputs through recorded derivation/output identities, not fresh flake installables. If roots or derivations are unavailable, report target-unavailable; do not evaluate latest source to replace them. Keep existing best-effort build recovery, rollback, termination and cache-publish ordering unchanged for eligible hosts. Each attempt's `rc` remains historical; campaign aggregate state is a separate latest-reconciled outcome per host with provenance. An empty retry is a no-op without a run, including when all remaining members are excluded.

Reboot is a distinct campaign continuation: default to eligible reboot-pending members only, apply exclusions and concrete names, preserve order/drain options and the fleet's reboot wrapper. Verify installed profile equals the campaign expectation from a fresh survey before rebooting; mismatches or unknowns block that host. A reboot command's success is not verification. Final verification surveys the eligible campaign members, including prior successes, against the bound system paths, without activation. A new observation of drift does not silently downgrade historical success into retry permission; surface it and require a new campaign for redeployment of a previously successful member.

**Decided source-movement policy:** a changed source blocks new deploy/retry/reboot dispatch, with recorded-versus-observed identity and a recommendation to create a new campaign. Read-only inspection and bound-target verification remain available without the original checkout. Close is administrative, records actor/time/reason, refuses while a linked mutation is live or uncertain, and prevents further deploy, retry, reboot or exclusion mutation. Close may record incomplete/failed/reboot-pending results and exclusions; it never asserts success. Reopening or rebinding is not supported.

**Alternatives:** retry the original selector against the live checkout silently changes members and paths. Re-activating every member wastes successful work and can trigger avoidable disruption. Inferring retry permission from drift confuses post-success changes with failed deployment. Allowing pinned retries after checkout movement is technically possible but is deliberately not the version-1 policy: explicit new-campaign acknowledgment makes source divergence visible.

### 4. Exclusions are persistent, explicit policy updates

Resolve exclusions at creation against the frozen selection and retain each exact name and reason, including selector `!` terms (with the selector term as a reason if no operator reason is provided). Store pre-exclusion membership so explicitly excluded selected members retain their intended target if deploy-capable. Distinguish non-deploy capability skips from operator exclusions; capability cannot be changed by unskipping.

An exclusion update supplies expected campaign generation, actor, timestamp, reason and exact names to add/remove. Append history and increment generation atomically; never edit initial membership or targets. Adding an unknown/unselected member is refused. Removing an operator exclusion permits only that member's original target, not a replacement source; it does not clear prior success. Replacing a reason is an explicit logged update. Default every deploy, retry, reboot and verification selection through the same effective exclusion projection. An optional selector only narrows it. Render excluded rows and reasons separately from eligible success/failure denominators; report both original and eligible counts so skipped hosts are never implied verified.

Serialize dispatch, close and exclusion updates; reject updates while a mutating attempt is live or uncertain so skips cannot promise to cancel already scheduled host work. Cancellation remains the existing explicit terminate action. For example, operator-alice may exclude `node-b` for maintenance and later remove that exclusion with a reason; `node-b` retains its original closure, and a successful `node-a` is never retried.

**Alternatives:** save a negative selector string and re-resolve it later; rejected because changing groups can change skip intent. Updating an in-flight exclusion without a scheduling barrier cannot guarantee the host has not already activated; reject rather than imply cancellation.

### 5. Two drift questions, independent expectations

Campaign views compare a fresh observed `current`, `booted` and `system_profile` to the campaign's stored system expectation. Latest-source views compare those same observations to separately evaluated expectations with their own source identity, cache provenance and timestamps. Show both named comparisons together when requested, not one unlabeled status and never a latest-source substitution for missing campaign data. Campaign identity is not `.expected.json` and a cache refresh never changes it.

Preserve no-snapshot, stale, unreachable, incomplete and per-host eval-failed precedence. Add `expectation-unknown` for an absent/unusable per-host expectation; `expected_source: none` is never in-sync/clean or a successful verification. Display boot observations even when expectation is unknown, but do not turn them into target success. Installed profile equal to target with a different current path is reboot-pending; current equal to target with boot-critical booted differences retains reboot-pending; known noncritical booted differences retain activated. Missing boot facts remain conservative. A reboot-pending deployment is successful staging but not final live verification. Final verification reports complete only with fresh observations proving the eligible targets running and no remaining reboot requirement; dry activation never supplies that proof.

A legacy revision-only expectation cache may support ordinary latest-source reads only under its existing same-clean-revision guard; it cannot prove nested-input identity or campaign equality. Campaign-aware latest-source comparison requires a complete content-identity match or explicit evaluation from a newly captured snapshot. A stale, missing, corrupt, dirty-ambiguous or identity-incomplete cache reports unknown unless replaced by a successful explicit evaluation. Partial evaluations remain per-host errors and are not cached. Record the evaluated latest-source identity, even if the checkout moves during the read; label that source movement rather than calling an old snapshot “latest” unqualified.

**Alternatives:** replace the global expected cache with the campaign map; rejected because it hides legitimate newer-source drift. Treat no expected path as equality; rejected because absence proves nothing. Flatten staged and running outcomes into success; rejected because a reboot is still required.

### 6. Add lifecycle surfaces without changing existing commands

Proposed CLI: `mandala campaign create --limit <selector>` binds and starts the first deployment attempt in one operation; `campaign create --limit <selector> --preview` binds and displays the target without an attempt or host effects; `campaign inspect <id>` lists target, source, exclusions, outcome provenance, attempts and verification; `campaign retry <id>` starts remaining failed/pending work, including work left pending by a creation preview; `campaign exclude <id> --add/--remove <names> --reason <text> --generation <n>` updates policy; `campaign reboot <id>`, `campaign verify <id>` and `campaign close <id> --reason <text>` complete the lifecycle. Reads support JSON; identifiers are validated/confined before filesystem access. Real create/retry/reboot require normal explicit mutation confirmation and display the target digest, exact eligible names and campaign generation before dispatch. Creation review precedes first-attempt dispatch; cancellation or a confirmation refusal launches no work. Existing deploy, drift and run attachment remain valid and do not implicitly join a campaign. An optional `drift --campaign <id>` adds the two labeled comparisons without changing unqualified legacy output fields except the necessary truthful unknown status.

TUI adds a campaign list/detail route beside Runs. Show source identity/moved status, original/eligible/excluded counts and reasons, pending/failed/confirmed/reboot-pending counts, attempt links and both drift bases. Creation, retry, exclusion changes, reboot and close have explicit review dialogs; the creation dialog reviews the captured target before confirming create-and-deploy and also offers a no-host-effects preview; run links still attach through the normal deploy screen. Inspecting a closed campaign never launches work. Do not choose keybindings by reusing an occupied action.

Add MCP tools `campaign_create`, `campaign_inspect`, `campaign_retry`, `campaign_exclude`, `campaign_reboot`, `campaign_verify`, `campaign_close`; add optional `campaign_id` to `drift`. Real creation binds and starts the first attempt. Creation defaults to `dry_activate=true` for safe target review: this dry creation preview binds and returns the target without an attempt or host effects, leaving real work pending. Retry retains its existing dry-activation default and semantics. Non-dry creation, non-dry retry and every reboot require `confirm` equal to the exact resolved eligible comma-joined limit, checked with campaign digest/generation again at dispatch. Refusals return `required_confirm`, eligible names and generation without launching. Policy updates and close require explicit generation and confirmation of campaign id; stale generations refuse without effects. Audit local policy mutations as well as fleet mutations. Do not change existing tool defaults, existing `deploy_status` detail budgets or legacy argument/result fields; add campaign links to run status, and return detailed paths via paginated campaign inspection with explicit total/elision, not default run summaries.

**Alternatives:** overload `deploy_status` into a mutating lifecycle interface; rejected because attachment/status must stay read-only and bounded. Automatically turn every old deploy into a campaign; rejected until the additive lifecycle is implemented and reviewed separately. Bind-only create followed by retry or a separate start verb separates review from effects but adds a mandatory second action; rejected in favor of decided create-and-deploy semantics. Explicit creation preview and the unchanged real-mutation confirmation gate preserve safe review without making retry the normal initial execution command.

### 7. One policy below every frontend, independent of reload

The shared core owns target capture, source comparison, eligibility, exclusion generation, persistence and confinement. A live context leader serializes mutations and emits the normal activity/audit settlements; standalone CLI uses the same per-campaign interprocess lock and generation compare-and-swap, not a parallel policy. At most one mutating continuation is active per campaign. Locks are not held while waiting for interactive confirmation; dispatch revalidates everything after confirmation. A refused stale generation requests a fresh review, never auto-updates confirmation.

Checkout watching and `reload` still refresh the latest inventory once per context, but cannot invalidate, overwrite or rebind a campaign snapshot. A promoted context reads durable records and reconciles existing supervisor-owned runs; it does not repeat a mutation because an RPC result was lost. Read-only inspection/verification may be retried under existing read rules only when doing so cannot create a new registered mutation; no lifecycle write is auto-replayed. This is local consistency, not HA rollout orchestration.

**Alternatives:** cache campaigns only in the warm leader or serialize only within one frontend; rejected because restarts, standalone CLI and follower calls must not lose exclusions or double-schedule hosts.

## Delivery, Verification and Approval

Implement in small additive steps in `tasks.md`: protocol and pure policy first, frozen capture and execution second, shared projections and frontends last. No consumer switches until old/new golden records and effect-isolated tests pass. Use temporary source repositories, nested local inputs/submodules, a fake inventory, stub Nix/SSH/reboot/survey processes and isolated state directories; no live fleet or cache.

The test matrix must cover source edits during capture and after binding, two dirty contents at one revision, nested input/submodule pointer movement without root revision movement, partial build/activation failure, exact-path retry with successful siblings untouched, staged success excluded from retry, dry previews, explicit skip add/remove/reason updates, dispatch races, orphaned ownership, close/retention, corrupt/future manifests and stale/missing expectation caches. Verify CLI/TUI/MCP judgments and confirmation refusal parity from shared fixtures, and the profile-wrapper versus system-toplevel distinction. The targeted gates are `nix build .#checks.<system>.fake-fleet` and `nix build .#packages.<system>.mandala-rs` (workspace tests), plus `nix fmt -- --check .` and `nix flake check`; `flake.nix` is authoritative for systems and target names.

## Decision Status and Remaining Approval

The three version-1 choices are settled:

- **Source movement:** refuse new mutating continuations and require a new campaign; see decision 3 for the rejected pinned-retry alternative and rationale.
- **Retention:** protect open campaigns' targets, roots and linked runs until explicit close; see decision 2 for rejected expiry/lease alternatives and rationale.
- **Initial execution:** create-and-deploy in one step, with the same real-mutation confirmation gate as deploy runs and an explicit dry creation preview for target review; see decisions 3 and 6.

No open choice remains among these three decisions. Their approval does not authorize implementation or consumer migration. Obtain the remaining plan and implementation approval through the coordinator before implementation.
