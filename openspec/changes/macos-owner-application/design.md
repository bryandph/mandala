## Context and Sources

Read this plan after `../vm-member-host-application/design.md`. Its ownership, publication/transport guards, selection expansion, owner locking, one-graph/build and recovery requirements remain authoritative except for the explicitly extended backend/pair and adapter scope below.

Current boundaries are in `schema/member.nix`, `flake-modules/fleet.nix` (NixOS configurations plus extra members), `flake-modules/deploy.nix` and `lib/projections/deploy-nodes.nix` (NixOS-only activation). `crates/mandala-core/src/engines/deploy.rs` creates prebuilt system profiles but currently reports host-only confirmation. `crates/mandala-deploy/src/{deploy,data,lib,push}.rs` holds copy, explicit profile paths, canary/wait/confirm, rollback and NixOS staging. This plan adds a typed adapter boundary; it does not infer Darwin support from existing settings.

Controller identity rules are in `docs/convention.md`, `tests/controller-platform.nix` and `deployment.controllerSettings`. Capacity belongs to `lib/builders.nix`, `modules/builders.nix` and `docs/builders.md`; the nix-darwin builder adapter configures the daemon, not deployment or VM lifecycle.

Public upstream evidence, read at fixed revisions:
- [deploy-rs flake.nix](https://github.com/serokell/deploy-rs/blob/6d3087eedff75a715b40c0e124ba15d2dd7bec28/flake.nix): `activate.darwin` wraps `system.build.toplevel` with `HOME=/var/root $PROFILE/activate`; `activate.custom` supplies both deploy-rs entry points. Darwin systems are included in the upstream output systems.
- [deploy-rs activate.rs](https://github.com/serokell/deploy-rs/blob/6d3087eedff75a715b40c0e124ba15d2dd7bec28/src/bin/activate.rs): profile set/rollback through `nix-env`, previous `deploy-rs-activate` reactivation, and `notify::recommended_watcher` canary creation/removal implement magic rollback without a Linux-only inotify API. Error strings mentioning inotify are not a platform restriction. Root/system resolves to the Nix system profile, and explicit profile paths are supported.
- [nix-darwin activation-scripts.nix](https://github.com/nix-darwin/nix-darwin/blob/ff0e21a414d4547183396da1b44a66f2577b65e9/modules/system/activation-scripts.nix): root activation changes launchd/system configuration and updates `/run/current-system` after script completion. It is not a general transaction over data or external effects.

These sources establish an applicable design, not a successful live Darwin deployment. The vendored controller files identify their provenance but include subsequent canary/cancel and process-ownership handling; consumers supply the actual deploy-rs pin. Qualification must test that pin's protocol and Darwin watcher behavior rather than assuming byte-identical upstream/controller implementations.

## Goals and Non-goals

Manage one explicit macOS owner unit and its Linux guests through the owner's own module while retaining the single fleet evaluation/build and truthful runtime evidence. Keep NixOS behavior and facts-only Darwin members unchanged unless explicitly enrolled.

Non-goals: implementation, adoption, guest transport/execution, generic macOS management, nested hosting, first-time VM creation without a recoverable runtime, arbitrary data rollback and live deployment.

## Decisions, Alternatives and Rationale

### 1. Enroll an explicit nix-darwin configuration, not a platform tag

Add consumer `darwinConfigurations.<member-id>` discovery beside `nixosConfigurations`; require the same validated `config.host` schema, matching canonical ID and Darwin platform/build system. Merge NixOS, Darwin and extra-member namespaces with collision rejection, even if duplicate values appear equal. An enrolled standalone owner enables `deployment.deployRs.enable`, targets root (possibly through a distinct SSH login/sudo), and supplies a compatible artifact and backend manifest. Extra facts-only entries do not become deployable from `platform = "darwin"` or a builder facet. Moving a facts-only ID into Darwin configuration discovery requires removing its duplicate extra-member declaration explicitly.

Choose one application-unit adapter tag `darwin-system` in aggregate unit metadata and backend enum `darwin-module` on `host.vm.backend`. Owner platform is Darwin; guest platform is NixOS with an explicit Linux build system and consumer configuration. The module declares qualified owner/guest systems. Ownership validation remains fleet-wide: existing standalone, directly managed owner, no cycles/self/nesting, sorted derived guest index and manifest equality. The NixOS backend remains `nixos-module`, not a generic command escape hatch.

**Alternatives:** infer enrollment from OS/build capacity (dangerous implicit management); keep opaque extra-member installable strings (weak configuration validation); add a second macOS fleet/evaluation (breaks one graph). Reject them. Additive configuration discovery preserves existing opt-in boundaries and toolchain ownership.

### 2. Build one owner artifact with guest dependencies

Choose a deploy-rs activatable wrapper around the consumer's nix-darwin `config.system.build.toplevel`. The immutable owner artifact contains the underlying system path, Darwin-native `activate-rs`, `deploy-rs-activate`, and a versioned typed manifest referencing every managed guest's immutable closure/image. The manifest binds owner/guest IDs, backend/runtime instance, guest system, desired image/closure digest, readiness contract, observation protocol and recovery policy. Owner/guest references must be acyclic; no activation-time discovery of a different configuration.

Extend pure deploy-node and batch projections to accept Darwin configurations additively, using the same flattened settings and controller-platform variants. Emit one owner system-profile node, never guest nodes; raw static groups still do not expand a guest-only group. The version-2 aggregate carries adapter tags and installable-reference strings, not derivations. Readers must support the adapter explicitly; unknown adapters fail before build/mutation. The existing version-2 ownership envelope suffices with this required capability check; do not silently treat unknown adapters as NixOS. Non-opted-in version-1 fleets keep their bytes.

Native selection maps guest/direct-owner requests to one owner before approval, showing requested and affected siblings, immutable artifacts, restart/re-image policy, disk/key replacement and recovery limits. Bind revision and all impact to approval. Conflicting owner/sibling exclusions fail. Build all selected owner wrappers and transitive Darwin/Linux dependencies in the one existing batch invocation; build-platform and target-system distinctions remain explicit. Missing cross-system capacity or guest build failure prevents that incomplete owner from copy/apply. Copy the full verified wrapper closure to the owner store only; preserve fastConnection/substitution policy. No rebuild, flake evaluation or image construction is allowed during application.

**Alternatives:** a guest build pipeline or target-side darwin-rebuild would break eval-once; a manifest without store references permits missing inputs. Choose direct immutable dependencies and the existing batch.

### 3. Keep deploy-rs, with a bounded Darwin wrapper

Use deploy-rs `activate.custom` with the same root activation semantics as upstream `activate.darwin`, extended to prepare/apply/verify the owner's guest module before successful return. Run the prebuilt underlying Darwin system's `activate` with root HOME and controlled environment, not a command that rebuilds. The wrapper invokes only the declared owner adapter. Its successful return means owner runtime checks and all required guest running identities/readiness passed; only then may activate-rs create its canary and the controller confirm by removal. Retain the controller's stale canary/cancel handling, concurrent waiter, bounded activation/rollback ownership and termination semantics. No custom canary protocol or unbounded background verifier.

Use explicit `profilePath = "/nix/var/nix/profiles/system"` in the adapter contract, root privileges and a declared writable owner-local temporary directory. Preserve wrapper versus underlying Darwin system path separately: installed system profile may identify the wrapper, while `/run/current-system` identifies its underlying system. Verify against that mapping, not raw path equality. A completed script/profile switch alone is not sufficient evidence.

The previous system-profile generation must also contain compatible restore/verification entry points. An arbitrary pre-Mandala Darwin profile usually lacks `deploy-rs-activate`; automatic adoption/bootstrap of that profile is not claimed. Reject before mutation until a separately approved bootstrap supplies a recoverable prior wrapper/runtime. When deploy-rs reactivates a prior wrapper, it must read the durable active transaction and restore retained previous runtime instances, not blindly regenerate a fresh VM from the old image. Root-owned recovery metadata is authoritative, validated against owner, manifest and transaction; arbitrary files or commands cannot choose recovery paths.

Darwin does not use NixOS switch-inhibitor checks, switch-to-configuration, boot-loader staging or GNU-only commands from the existing NixOS staging helper. Explicit boot mode (including per-run override), unsupported activation modes and a dry path that cannot guarantee no effects fail before copy/mutation. Supported dry activation may build/copy and inspect but must not execute the upstream default custom dry command as live activation, change profiles, restart launchd/VMs or write runtime recovery state. Darwin staging of a prebuilt guest image may be an explicitly approved pending disposition; it is not a NixOS reboot-pending owner outcome. This first adapter requires live owner activation; it has no generic boot-only owner operation.

**Alternatives:** plain upstream activate.darwin confirms only a host script; shelling out to darwin-rebuild risks new evaluation; abandoning deploy-rs duplicates recovery/confirmation. Choose a custom wrapper preserving deploy-rs wire behavior. Applicability is conditional on conformance, not a blanket assertion of macOS magic-rollback reliability.

### 4. One module/image-managed Linux guest backend

The consumer's owner module owns launchd/VM-manager lifecycle and image selection. The typed `darwin-module` adapter implements bounded inspect, prepare, apply, verify and restore operations through the owner transport only. It declares exact supported systems, restart/re-image triggers and recovery prerequisites. A module/configuration change may restart the guest or instantiate a new disk from a prebuilt immutable image; instantiation is runtime application, never image building. No real VM product is required or pinned.

Inspect must query an owner-local authoritative VM-manager record or root-owned runtime manifest maintained from observed lifecycle events. For each guest record immutable image/generation, runtime instance/boot epoch, selected disk incarnation, process/manager identity and bounded readiness. A manifest written only from desired configuration is insufficient. Join observations to the active instance; stale records, PID reuse, unknown identity, wrong image or a stopped VM cannot pass. Readiness must include runtime health and the declared owner-side service/manager probe; power-on alone is insufficient. No guest SSH, guest-exec, direct guest builder connection or foreign switch binary. Observation and status interfaces return typed data, not parsed success prose.

A guest is deployed only when its desired image/closure is observed in the active instance and declared readiness passes. Explicit stage-only intent with unchanged running identity is pending, separately counted; a failed expected live re-image/restart cannot be reclassified pending. Inspect reports desired, staged, running and previous separately. Changed guest host keys are incidental runtime state, not fleet transport identities; no pins, TOFU or externally managed known-hosts exception is introduced for a VM.

**Alternatives:** trust an image symlink or owner's profile (does not prove running generation); guest SSH readiness (violates authority); assume launchd job success means guest readiness (too weak). Choose owner-side identity plus independent declared readiness.

### 5. Recovery retains runtime incarnations, not just images

Before any profile/disk mutation, hold the owner-enforced cross-controller lock and atomically persist/root the prior wrapper, underlying system, manifests, runtime/boot identities, image pointers, disk incarnations and readiness contract. Protect mutable prior disks outside Nix GC as well as immutable store paths. The transaction covers copy/apply/verify/recover; another controller or direct owner/guest selection cannot race it. Reconcile interrupted transactions by observation before admitting new mutation. Recovery commands and observations are bounded; no detached recovery or prohibited post-cancellation effects.

Require module support to retain and restart the prior runtime incarnation/disk, or an equivalent qualified snapshot that preserves identity. Re-image into a separate new disk/runtime, never overwrite the sole prior disk. Record the new disk/key incarnation without exporting private keys. If the real module destroys its old disk or host key irretrievably, it fails this backend's recovery prerequisites and mutation is refused. First creation without prior runtime remains refused as in the parent change.

On apply/readiness/confirmation failure with auto-rollback, restore previous wrapper/system effects as supported, select the retained prior guest runtimes/disks, restart and verify every prior identity/readiness. A reboot creates a new boot epoch, so recovery compares the previous image and disk/runtime lineage, not an impossible identical PID/boot timestamp. A retained disk may restore its old host key; do not promise it when the module regenerates keys on every start. Host keys are never a deployment-success criterion or guest transport trust. Recreating a fresh disk from an old image restores neither prior runtime incarnation nor old data/key and must not be labelled rolled-back.

Plainly: the owner profile, declared system/module state, image selection and retained guest runtime lineage can be restored and verified. Arbitrary nix-darwin activation effects, writable application data, in-flight jobs, external state and data written to a replacement disk are not automatically undone. Retaining an old disk is not a general data snapshot guarantee. Preview these limits before approval; backend qualification refuses irreversible owner effects needed for claimed recovery.

Host-only magic rollback is insufficient. If a sibling cannot be restored, mark partial-recovery/failed; if state cannot be observed, mark unknown/recovery-required. Preserve primary and recovery diagnostics independently and keep the run nonzero. Auto-rollback disabled means failed/unrecovered, not fictitious restoration. Independent successful owners remain untouched.

**Alternatives:** in-place destructive re-image is simpler but cannot meet the parent recovery requirement; recreating only the old image lies about identity/data recovery; introduce an irreversible mode that calls itself rolled-back would weaken the approved contract. Choose retained-runtime support and fail closed. Supporting destructive-only modules would require a separate decision/change, not a hidden relaxation here.

### 6. Controller identity is independent of target OS

Use the existing fleet < runtime-controller OS < sorted groups < member precedence for owner copy, inspect, lock, activate, verify, confirm and recovery. A Darwin controller selects `controllerSettings.darwin`; a Linux controller deploying the same Mac selects `linux`. Missing configured entries/unsupported runtime OS fail without ambient identity fallback. Keep identities as path strings, strict IdentitiesOnly/IdentityAgent rules, and direct-tool explicit variant selection. The target's Darwin platform never selects the controller key.

For self-deployment, choose the normal owner SSH endpoint even when controller ID equals owner; do not infer local activation, localhost or bypass credentials/approval. Require a reachable authenticated owner endpoint and privileges or fail preflight. The deploy controller runs outside module-managed services whose restart would kill it; otherwise reject unsafe self-deployment before mutation. Retain prior controller executable/closure, run registry and recovery references until settlement. Connection loss is not success: target magic rollback plus durable recovery record handles reconciliation, and a lost controller records interruption/unknown rather than inventing verified recovery.

Builder self-exclusion remains based on explicit controller member ID, not runtime OS or target adapter. The local Mac daemon supplies its advertised Linux capacity; other controllers build through the Mac's strict owner endpoint. Capacity, systems/features/lanes and actual daemon dispatch are explicit on owner `host.builder`. The guest is never a route or duplicate capacity advertisement. No new inference of emulation or additional SSH trust kind. Existing nix-darwin builder module output is configuration, not proof that live daemon dispatch works.

**Alternatives:** implicit local self-activation would fork transport/security semantics; selecting identity from target OS breaks cross-platform controllers. Preserve one owner endpoint and existing controller selection.

### 7. Durable contracts and effect-isolated qualification

Extend the parent version-2 unit metadata with `adapter = "darwin-system"`, wrapper/system path mapping, profile path, backend/manifest capability, runtime and disk incarnation, desired/staged/observed identities, readiness, recovery retention and data/key limitations. Pure aggregate data describes capabilities and references; runtime observations live in durable deploy records. Persist before mutation and reconstruct outcomes without reevaluation. Existing event versions/unknown-field handling and old-record absence remain unchanged; old host-only confirmation never proves VM deployment. Do not overload NixOS boot-default snapshot meaning for a Darwin wrapper.

Proposed additive checks: `darwin-owner-schema`, `darwin-owner-projection`, `darwin-owner-controller`, `darwin-owner-state`. Use acme/globex fake fleets, faithful typed Darwin configuration stubs, pure JSON expectations and injected Nix/SSH/VM-manager effects. Assert exact effect traces, one graph/build, dependency isolation, target-platform executables, no guest route or activation-time construction, lock contention, stale observations, wrapper/system mapping, first-adoption refusal, dry/boot refusal, staged versus failed restart, cancellation, host-only rollback, disk loss and sibling partial recovery. Native Rust tests cover orchestration/protocol with fake executables, never a live Mac or guest. Real pinned Darwin module evaluation and watcher/rollback integration are separate opt-in qualification gates before production support is declared.

**Alternatives:** real-fleet tests would violate effect isolation and be unreproducible; mocks alone cannot qualify a live virtualization module. Choose isolated mandatory tests plus explicit, separately authorized runtime qualification.

## Approval and Open Items

All choices above are proposed plan decisions; completeness does not authorize implementation or deployment. No blocking scope question remains for writing these artifacts. Before implementation, reviewers must approve the additive enrollment/backend ABI, explicit boot refusal, recoverable-wrapper adoption prerequisite and retained-runtime restriction.

Concrete consumer VM modules and their exact manager observation/snapshot APIs are intentionally not selected. Options are (A) supply a module meeting retained-runtime/owner-observation conformance, recommended, or (B) shape a separately approved weaker destructive-reimage recovery contract. This plan refuses B rather than quietly claiming recovery for an unsupported product.
